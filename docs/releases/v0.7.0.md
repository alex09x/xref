# XRef v0.7.0

**Where a process waits and what it allocates, profiles that follow a daemon
or every instance of a benchmark, frames named in libraries and the kernel,
per-thread profiles from `perf record -- CMD`, and `live profile` on Apple
Silicon macOS.**

## Where a process waits (`xref live sched`)

```sh
sudo xref -b ./app live sched --pid PID --duration 10s
sudo xref -b ./app live sched --pid PID --duration 10s --out wait.xprof
xref -b ./app profile report wait.xprof
```

- Off-CPU time by the stack each thread blocked in, unwound from the user
  registers at the switch-out, down to the library call
  (`main -> wait_tick -> libc.so.6:poll`).
- Voluntary and preempted context switches, wakeups per second, and every
  system call (`raw_syscalls` tracepoints) with its count and a latency
  histogram (mean, p50, p99, max). `--no-syscalls` leaves them out.
- Records of all threads are applied in timestamp order; a loss or a kernel
  throttle breaks the pairing of the affected thread instead of joining an
  entry to a later exit, and marks the recording partial.
- `--out` keeps an off-CPU `.xprof` weighted by nanoseconds for
  `profile report` and `profile diff`.

See [docs/cli/live-sched.md](https://github.com/alex09x/xref/blob/v0.7.0/docs/cli/live-sched.md).

## Allocations by call site (`xref live alloc`)

```sh
sudo xref -b ./app live alloc --pid PID --duration 10s --out alloc/
xref -b ./app profile diff alloc-before/live.xprof alloc/live.xprof
```

- Uprobes on the entries and returns of `malloc`, `calloc`, `realloc` and
  `free` of the allocator the process maps (the executable, then other
  libraries such as an interposed jemalloc, then the C library;
  `--allocator PATH` picks one). Each allocation is unwound at once.
- Stacks and functions by allocations, bytes and the bytes still live at the
  end of the capture; only the outermost allocator call of a thread counts
  (glibc's `realloc` calling `malloc` is one call), and a moving `realloc`
  frees the old block only if that address still holds it.
- `alloc.xprof` (bytes allocated) and `live.xprof` (bytes still live) for
  `profile report` and `profile diff`, which refuses to compare different
  measures.

See [docs/cli/live-alloc.md](https://github.com/alex09x/xref/blob/v0.7.0/docs/cli/live-alloc.md).

## Profiles that follow processes (`live profile --follow-children`, `--comm`, `--argv-match`)

```sh
sudo xref -b ./app live profile --pid PID --follow-children --duration 12s
sudo xref -b ./app live profile --comm app --duration 12s --out bench.xprof
```

- `--follow-children` also samples the processes a sampled process forks
  without exec, a daemon started by `fork`, `setsid` and a second `fork`
  included: a process is accepted when its parent, process group or session
  belongs to the target's family.
- `--comm NAME` and `--argv-match TEXT` add processes with that name or
  command line as they start; without `--pid`, xref waits for the first one.
- Every added process must run the same executable file (device and inode);
  others are refused and counted. Each process keeps its own address layout,
  and a process is identified by its PID and start time, so a reused PID is
  not mistaken for it.

See [docs/cli/live-profile.md](https://github.com/alex09x/xref/blob/v0.7.0/docs/cli/live-profile.md).

## Names in libraries, the kernel and the vDSO; diff by name

- Profile frames in shared libraries are named from their `.symtab` or
  `.dynsym`, a debug file found by build ID or `.gnu_debuglink`, or
  debuginfod when `DEBUGINFOD_URLS` is set. An IFUNC such as glibc's `memset` is named after the variant
  its resolver selects on this machine.
- Kernel frames are named from `/proc/kallsyms` (core text only) when
  readable, and vDSO frames from the process's own vDSO.
- `profile diff` pairs library and kernel functions by name: a function
  present on one side only is 0% on the other (`memset 99.85% -> 0.00%`,
  `only_before`). Mismatched executables are reported with both SHA-256
  values, and `func` names the symbol at an address.

## Threads and `perf record -- CMD` (`profile import`, `profile report --by thread`)

```sh
perf record -F 999 -g -o perf.data -- ./app ARGS
xref -b ./app profile import --out app.xprof --pid PID perf.data
xref -b ./app profile report app.xprof --by thread
```

- A recording of a program started by `perf record -- CMD` is imported with
  only `--pid`: xref finds the exec of `perf-exec` into the target and leaves
  out what ran before it. Every thread of the process is kept; `--tid`
  keeps only some.
- `profile report --by thread` lists each thread with its hottest functions;
  the JSON report has a `threads` list.
- `perf script` text needs no `--maps` when written with
  `--show-mmap-events`, and headers without an event name
  (`-F comm,pid,tid,time,ip,sym,dso`) are read.
- `profile annotate` refuses weighted recordings (heap, alloc, off-CPU).

See [docs/cli/profile-import.md](https://github.com/alex09x/xref/blob/v0.7.0/docs/cli/profile-import.md).

## `live profile` on Apple Silicon macOS

```sh
xref -b ./app live profile --pid "$(pgrep -n app)" --duration 12s --out after.xprof
xref -b ./app-before profile diff before.xprof after.xprof --other ./app
```

- On macOS, `live profile` runs the system's `/usr/bin/sample` on the
  process and saves its call tree as an `.xprof`. The binary must be the
  process's executable: both `LC_UUID` values must be present and equal.
- An arm64 Mach-O is read for its symbols and `LC_FUNCTION_STARTS` only, so
  `profile report`, `profile diff` (functions of two builds paired by names
  unique in both) and `--within` work; `annotate` and `--by
  block|line|instruction` need x86-64 code and are refused.
- `sample` is a timer over whole seconds with frame-pointer stacks and counts
  per frame: `--period`, `--event`, `--callers lbr|none`, `--max-samples`,
  `--tid`, triggers and process following are refused rather than ignored.
  System libraries live in the dyld shared cache and are attributed to the
  library, not to a function.

See [docs/cli/live-profile.md](https://github.com/alex09x/xref/blob/v0.7.0/docs/cli/live-profile.md).

## Limits

- `live sched` and `live alloc` need root (perf kernel events, tracefs,
  uprobes). `live alloc` stops a thread twice per allocator call; a program
  that allocates millions of times a second slows down while observed. It
  sees only an allocator that exports `malloc` and `free`.
- Threads of `live alloc` and processes of `--follow-children` are found by
  scanning `/proc` every 25 ms and by fork records: a thread that starts and
  ends between two scans is not observed, and the first milliseconds of a
  short-lived process can be missed.
- A record loss in `live sched` or `live alloc` has no timestamp of its own;
  the pairing of the affected thread is reset at the nearest record, so a
  call spanning the loss is left out, and the recording is marked partial.
